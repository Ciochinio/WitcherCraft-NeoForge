▶ How to add and connect a new GUI

Every navbar tab needs three things to become a real, working page: a NAV entry (this tool), a GuiPage class (code), and being registered so the shell can find it. Follow these steps for a new page, e.g. "crafting":

  1. 1. Add the nav tab. Click + Nav tab above, set its pageId (e.g. crafting), a labelKey (a lang key you'll add to en_us.json), and optionally an icon texture path. Reorder with the arrows. It will show as "Coming soon" in-game until step 3.
  2. 2. Give it a background (optional but recommended). Set the tab's background field to a texture path, e.g. witchercraft:textures/gui/shell/backgrounds/crafting.png - author that PNG at the design canvas's aspect ratio (16:9 by default) and drop it in src/main/resources/assets/witchercraft/textures/gui/shell/backgrounds/. Leave it blank to use the shared fallback BG.
  3. 3. Write the page class. In the base package net.redboltmedia.witchercraft (so it opens as a code element in MCreator), create e.g. CraftingPage.java implementing GuiPage: 
    public class CraftingPage implements GuiPage {
    public String id() { return "crafting"; }
    public Component navLabel() { return Component.translatable("gui.witchercraft.shell.nav.crafting"); }

    public void render(GuiGraphicsExtractor g, int x, int y, int w, int h,
                        int mouseX, int mouseY, float partial) {
        // x,y,w,h = the content region (design coords, below the navbar).
        // Draw with g.fill(...) / g.text(...) / g.blit(...), same idioms as
        // any MCreator-generated screen. Look at PerkPage.java for a full
        // example, including how it fit-scales an authored layout into
        // this region and how it reports hover tooltips via pollTooltip().
    }
}
  4. 4. Register it. In WitcherGuiPages.java's static block, add: 
    CraftingPage crafting = new CraftingPage();
CUSTOM.put(crafting.id(), crafting);
    This is the ONLY code wiring step - the shell already routes clicks, tooltips, Esc, and the tab highlight for any id present in both NAV and this map.
  5. 5. (Optional) build it its own placer tool. If the page has authored geometry (slots, buttons, art placement) rather than just static content, copy equip-grid-placer.html or tree-node-placer.html as a starting point, point its "regenerate" output at a new CraftingLayout.java data class, and have CraftingPage read from it - exactly how Skills is built from PerkEquipLayout + PerkTree.
  6. 6. (Optional) give it a keybind default. In WitcherGuiKeybind.java, add an entry to the DEFAULT_KEYS map ("crafting", GLFW.GLFW_KEY_...) - or leave it out and it stays unbound by default (set in Controls). Per-page keybinds are auto-generated from NAV[], so nothing else is needed here.
  7. 7. Add lang keys. Add labelKey (and any strings your page uses) to both src/main/resources/assets/witchercraft/lang/en_us.json AND the matching language_map.en_us block in witchercraft.mcreator (MCreator's own copy) - keep them in sync.

Reminder on client-only limits: this shell (and every page in it) is CLIENT-SIDE, opened with setScreen, no server menu. A page may freely call read-only procedures that just report player state (like PerkPage calling CharacterAbilitiesSkillPointsAvailableProcedure.execute(entity)). Anything that CHANGES server-authoritative state (learning a perk, moving an item, spending points) must go through a network message handled server-side - see PerkEquipGuiButtonMessage for the pattern (a buttonID-encoded message, validated and applied server-side, mirrored optimistically or just re-read next frame client-side). Do not call a mutating MCreator procedure directly from a page - on the client it will often no-op, desync, or throw, since most such procedures assume a server-side ServerLevel/ServerPlayer context.
